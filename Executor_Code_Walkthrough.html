The Planner turns the question into an ordered list of steps. The Executor runs once for every attempt of every step. When all steps are done, the Critic independently re-checks the numbers. The Executor is used on the standard route (the full AI pipeline); simpler questions take model-free routes.

2. What happens in one call overview of executor_node

  1. Read the state

    Which question, which step of the plan, and how many times this step has already been tried.

  2. Show progress

    Writes "Executing step 2/4 ..." (or "Retry 1/3 ...") to the database so the Analyses page updates live.

  3. Build the prompt

    Question + dataset profile + results of earlier steps + this step's goal + the last error, if any.

  4. Ask Gemini for code

    llm_client.call_tool() forces Gemini to answer through the submit_code tool: reasoning, a plain-English formula and a Python script. Falls back to Llama if Gemini fails.

  5. Run it in the sandbox

    get_runner() picks the Docker sandbox, the CSV is copied in read-only, and the script runs in a fresh container with no network.

  6. Save the evidence

    One ExecutionLog row per attempt: code, stdout, stderr, result, charts, data slice. This is what the Audit trail shows.

  7. Decide what next

    Success: move to the next step. Failure: retry with the error message. Third failure: stop the whole run.

CODE_TOOL_SCHEMA (lines 12-34)

Not a function, but the most important definition in the file. It is a JSON Schema that tells Gemini the exact shape of its answer. Because the call is forced to use this tool, Gemini cannot reply with free text; it must fill in three fields:

4. Functions in executor.py

_prior_results_summary

executor.py · helper
def _prior_results_summary(step_results: list[dict]) -> str

Turns the results of the steps already finished into short text, so Gemini knows what has been computed and does not recompute it.

Inputs

step_resultsList of finished steps. Each is a dict with step_index, description, result.

Returns

A string, one block per step: Step 0: ...  result: {...}. If nothing has run yet, "(none yet)".

Step by step

  1. If the list is empty, return "(none yet)" (first step of the plan).
  2. Otherwise build one line per step with its index, description and result.
  3. Join the lines with newlines and return.

Uses r.get('result') instead of r['result'] so a step without a result does not crash the prompt.

executor_node

executor.py · the LangGraph node
def executor_node(state: AgentState) -> dict

The main function. LangGraph calls it once per attempt of each plan step. It asks Gemini to write the Python code for the current step, runs that code in the sandbox, records the attempt, and tells the graph what to do next.

Inputs

stateThe shared AgentState: question_id, question_text, plan, step_index, retry_count, last_error, profile, csv_path, step_results.

Returns

A dict with only the fields that changed. LangGraph merges it into the state. There are three possible shapes (see section 5).

Step by step

  1. Lines 49-53. Read the state. Get the question id, the current step and the retry count. attempt_number is human-friendly (1, 2, 3) while retry_count starts at 0.
  2. Lines 55-58. Report progress. Build a message like "Executing step 2/4: Monthly revenue", or "Retry 1/3 on step 2 ..." on a retry, and save it with update_stage(). update_stage() is also a checkpoint: if the user cancelled the run, it stops here.
  3. Lines 60-72. Build the prompt. An f-string with the business question, the dataset profile (prompts.profile_block), the earlier results (_prior_results_summary) and this step's description and goal.
  4. Lines 74-80. Add the error on a retry. If the last attempt failed, its error text is appended with "Fix the root cause and provide corrected code". This is how the model learns from its mistake.
  5. Lines 82-91. Call Gemini. llm_client.call_tool() sends the system prompt EXECUTOR_SYSTEM (which contains the sandbox rules), the prompt above and CODE_TOOL_SCHEMA. The reply is a dict; the code takes out code, reasoning and formula_explanation.
  6. Lines 93-95. Run in the sandbox. get_runner() returns the Docker runner, seed_input_data() copies the CSV in as read-only input.csv, and run() executes the script and returns a SandboxResult.
  7. Lines 97-119. Save the attempt. Open a database session, insert an ExecutionLog row with the code, stdout, stderr, success flag, result, charts, reasoning, formula and data slice, commit, and keep its id. finally: db.close() always closes the session, even on an error.
  8. Lines 121-142. If it succeeded: build a step_result dict, add it to the list, move step_index forward, and reset retry_count and last_error.
  9. Lines 145-168. If it failed and this was the last allowed attempt: record the failed step and return failed=True with a readable failure_reason that includes the last error.
  10. Lines 170-173. If it failed but retries remain: return only retry_count + 1 and the error text. The graph sends the same step back to this function.

5. What executor_node returns

LangGraph merges the returned dict into the shared state, then route_after_executor() decides the next node.

OutcomeFields returnedWhat runs next
Successstep_results + this step, step_index + 1, retry_count = 0, last_error = NoneNext step, or the Critic if this was the last step
Failed, retries leftretry_count + 1, last_error = the stderr textExecutor again, same step; Gemini now sees the error
Failed, no retries leftstep_results + failed step, failed = True, failure_reasonEND: the run stops and the user sees the reason

6. Functions it calls in other files

llm_client.call_tool

llm_client.py · Gemini, then Llama
def call_tool(system, user_content, tool_name, tool_schema, tool_description, max_tokens=4096) -> dict

The model call used on line 82. It tries Gemini first and, if Gemini cannot answer, fails over to Llama so the run does not die mid-way.

Inputs

systemThe agent's instructions (EXECUTOR_SYSTEM).
user_contentThe prompt built in executor_node.
tool_name / tool_schemasubmit_code and CODE_TOOL_SCHEMA: the exact shape the answer must have.

Returns

The tool's arguments as a dict, e.g. {"reasoning": ..., "formula_explanation": ..., "code": ...}. Raises ProviderUnavailable if both providers fail.

Step by step

  1. If a GEMINI_API_KEY is set, call call_tool_gemini() in a loop.
  2. On a 429 (rate limit) or a retryable 5xx error, wait and retry, up to GEMINI_RATE_LIMIT_RETRIES (2) times.
  3. On any other error, including a reply without the tool call (MalformedOutput), stop trying Gemini.
  4. If failover is enabled and a LLAMA_API_KEY is set, make the same call on Llama.
  5. If that fails too, raise ProviderUnavailable listing why each provider failed.
  6. RunAborted (user cancelled, budget exceeded) is re-raised at once and never triggers failover.

llm_client.call_tool_gemini

llm_client.py · the actual Gemini request
def call_tool_gemini(system, user_content, tool_name, tool_schema, tool_description, max_tokens=4096) -> dict

Makes one request to Google Gemini and forces it to answer by calling exactly one named function.

Inputs

same as call_toolPassed straight through.

Returns

The function call's arguments as a dict.

Step by step

  1. runtime.checkpoint(about_to="llm"): stop if the run was cancelled or is over budget.
  2. Wrap the schema in a FunctionDeclaration.
  3. Call client.models.generate_content() with mode="ANY" and allowed_function_names=[tool_name], which means Gemini must call that tool.
  4. Record token usage and time with runtime.note_llm_call() (shown in the run trace and cost).
  5. Find the function call in the response and return its arguments.

get_runner

sandbox/runner.py
def get_runner() -> SandboxRunner

Chooses which sandbox to use from the SANDBOX_BACKEND setting.

Inputs

(none)Reads config.SANDBOX_BACKEND, default "docker".

Returns

A DockerSandboxRunner, or a SubprocessSandboxRunner for local development only.

Step by step

  1. "docker" returns the Docker runner, the real security boundary.
  2. "subprocess" is allowed only when SANDBOX_ALLOW_UNSAFE_SUBPROCESS=true; it is not isolated.
  3. Anything else raises SandboxUnavailable. It never quietly falls back to a weaker sandbox.

SandboxRunner.run

sandbox/runner.py
def run(self, question_id: int, code: str, step_index: int, attempt: int) -> SandboxResult

Runs one script safely and packages everything that came out of it. Called on line 95.

Inputs

codeThe Python script from Gemini.
step_index / attemptUsed to name this execution, e.g. s1_a2_3f9c....

Returns

A SandboxResult: success, stdout, stderr, exit_code, result, chart_paths, data_slice, timed_out and more.

Step by step

  1. Check the run is not cancelled, and that the sandbox is available.
  2. Reject the script if it is empty, too large (over 200 KB) or contains a null byte.
  3. Create a fresh folder for this execution with an out folder for charts.
  4. Run it with _execute() (Docker), then validate the charts with _collect_artifacts().
  5. Always delete the execution folder afterwards (finally).
  6. Success means exit code 0 and no timeout or cancellation. Add a hint if the process was killed (exit 137).
  7. Parse RESULT_JSON: and DATA_SLICE_JSON: from stdout and record the run in the trace.

DockerSandboxRunner._execute and _command

sandbox/runner.py · the container
def _execute(self, ws, exec_dir, code, timeout) -> _RawRun

Writes the script to main.py and starts a brand-new Docker container just for it.

Inputs

ws / exec_dirThe question's workspace and this execution's folder.
timeoutSeconds left, at most SANDBOX_TIMEOUT_SECONDS (60).

Returns

A _RawRun with stdout, stderr, exit code and flags for timeout, cancellation and overflow.

Step by step

  1. Write main.py and allow the container user to write to out.
  2. Start docker run with the locked-down options below.
  3. Hand the process to _supervise(), with a kill() that runs docker kill on the container.
  4. Always docker rm -f the container at the end.

Key options: --network none (no internet), --read-only, --cap-drop ALL, no-new-privileges, memory 512 MB with no swap, 1 CPU, a process limit, the data mounted read-only and only /workspace/output writable.

_supervise

sandbox/runner.py · the watchdog
def _supervise(proc, kill, timeout: float, output_limit: int) -> _RawRun

Watches the running container and kills it if it takes too long, is cancelled, or prints too much.

Inputs

procThe running docker run process.
killFunction that stops the whole container.
timeout / output_limitTime and stdout limits.

Returns

A _RawRun.

Step by step

  1. Start two _Pump threads that read stdout and stderr, keeping at most the limit.
  2. Every 0.2 s check: deadline passed? user cancelled? output far over the limit?
  3. If any is true, call kill().
  4. Add a clear note to stderr, e.g. [sandbox] execution timed out, which Gemini then sees on the retry.

8. Likely viva questions

Why force Gemini to use a tool instead of normal text?

A tool call returns structured JSON with fixed fields (reasoning, formula_explanation, code). Free text would need fragile parsing, and the model might wrap code in prose or markdown.

Why not just run the generated code with exec()?

The code is written by a model that read a user's question and a user's CSV, so it is treated as hostile input. It runs in a separate Docker container with no network, a read-only filesystem, no Linux capabilities, and CPU, memory, process and time limits.

What happens if the code crashes?

The stderr (error text) is saved and put into the next prompt with "Fix the root cause". Gemini gets up to 3 attempts per step (MAX_EXECUTOR_RETRIES). This is the self-correction loop.

What if Gemini is down or rate-limited?

call_tool() retries a 429 or 5xx error up to 2 times with a wait, then automatically switches to a Llama model. Only if both fail does the run stop with ProviderUnavailable.

How does the result get back from the container?

Through stdout. The script must print one line starting RESULT_JSON: and one starting DATA_SLICE_JSON:. Charts are saved as Plotly JSON in /workspace/output. The runner parses these and validates every file.

Why save an ExecutionLog for failed attempts too?

Auditability. The Audit trail shows every attempt, including the ones that failed and why, so nothing is hidden.

Why does the Executor not compute everything in one script?

The Planner splits the question into small steps. Each step is easier to get right, easier to verify, and a failure only retries one step instead of the whole analysis.

What stops a script from running forever or printing gigabytes?

_supervise() kills the container on timeout (60 s default), on cancellation, or when output exceeds the limit.
