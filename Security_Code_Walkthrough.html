1. hash_passwordhelper

lines 18-19
PurposeTurns a plain password into a one-way bcrypt hash so the real password is never stored.
Signaturehash_password(password: str) -> str
Inputspassword: the plain text the user typed at sign-up.
ReturnsA 60-character string such as $2b$12$... containing the algorithm, cost, random salt and hash.
ErrorsNone of its own. bcrypt raises ValueError if the password is longer than 72 bytes (see section 6).
How it works
  1. Encode the password to UTF-8 bytes (bcrypt works on bytes).
  2. bcrypt.gensalt() creates a new random salt, so two users with the same password get different hashes.
  3. bcrypt.hashpw() computes the hash (deliberately slow, to resist guessing).
  4. Decode the bytes back to a string so it can be saved in users.password_hash.
Used byrouters/auth.py → signup()
WhyHashing is one-way: even someone who reads the database cannot get the passwords back.

2. verify_passwordhelper

lines 22-23
PurposeChecks whether a typed password matches the stored hash.
Signatureverify_password(password: str, password_hash: str) -> bool
Inputspassword: what the user typed at login. password_hash: the value stored at sign-up.
ReturnsTrue if they match, otherwise False.
ErrorsNone of its own. bcrypt raises ValueError for a password over 72 bytes.
How it works
  1. Encode both values to bytes.
  2. bcrypt.checkpw() reads the salt from inside the stored hash, re-hashes the typed password with it, and compares the two in constant time.
Used byrouters/auth.py → login()
WhyThere is no way to "decrypt" a hash, so checking means re-hashing and comparing.

3. create_access_tokenhelper

lines 26-34
PurposeCreates the signed JWT login token returned after a successful sign-up or login.
Signaturecreate_access_token(user_id: int, email: str) -> str
Inputsuser_id and email of the user who just logged in.
ReturnsA JWT string with three parts, header.payload.signature.
ErrorsNone.
How it works
  1. Take the current UTC time.
  2. Build the payload: sub (the user id, as a string), email, iat (issued at) and exp (expires at = now + JWT_EXPIRE_MINUTES, 7 days by default).
  3. Sign it with JWT_SECRET_KEY using HS256 and return it.
Used byrouters/auth.py → signup() and login()
WhyThe server stores no session: the signature proves the token was issued by this server and not changed.

4. decode_access_tokenhelper

lines 37-41
PurposeChecks a token's signature and expiry and returns its payload.
Signaturedecode_access_token(token: str) -> dict
Inputstoken: the JWT sent by the client.
ReturnsThe payload dict, e.g. {"sub": "7", "email": ..., "iat": ..., "exp": ...}.
Errors401 Invalid or expired token if the signature is wrong, the token was edited, it has expired, or it is not a JWT.
How it works
  1. jwt.decode() verifies the signature with the secret key and checks exp.
  2. Only HS256 is accepted (algorithms=[...]), so a forged token using another algorithm is rejected.
  3. Any PyJWTError becomes an HTTP 401.
Used byget_current_user()

5. get_current_userFastAPI dependency

lines 44-55
PurposeWorks out who is making the request. Any endpoint that needs a logged-in user declares it with Depends(get_current_user).
Signatureget_current_user(authorization: str | None = Header(...), db: Session = Depends(get_db)) -> User
Inputsauthorization: the Authorization: Bearer <token> header, read by FastAPI. db: a database session from get_db.
ReturnsThe User row from the database.
Errors401 Missing bearer token (no header, or it does not start with "Bearer "); 401 Invalid or expired token (from decode_access_token); 401 User no longer exists (account deleted after the token was issued).
How it works
  1. Check the header exists and starts with bearer (case-insensitive).
  2. Split once on the space to get the token.
  3. Decode and verify it.
  4. Load the user by the id in sub.
  5. Return the user, or 401 if they no longer exist.
Used by103 endpoint parameters across the backend, e.g. /api/auth/me, /api/me/workspaces, and every team endpoint through get_current_team.
WhyChecking that the user still exists means a deleted account cannot keep using an old token.

6. get_current_teamFastAPI dependency

lines 58-79
PurposeWorks out which team the request is for and proves the user belongs to it. This is the core of multi-tenant isolation: one team can never read another team's data.
Signatureget_current_team(x_team_id: int | None = Header(..., alias="X-Team-Id"), user: User = Depends(get_current_user), db: Session = Depends(get_db)) -> Team
Inputsx_team_id: the X-Team-Id header (FastAPI converts it to an int). user: from get_current_user, so authentication always runs first.
ReturnsThe Team row. Endpoints then filter every query by team.id.
Errors400 X-Team-Id header is required; 404 Team not found; 403 Not a member of this team (including invited-but-not-accepted, since status must be active). Plus all the 401s from get_current_user.
How it works
  1. If the header is missing, return 400.
  2. Load the team; 404 if it does not exist.
  3. Look for a team_members row with this team, this user and status == "active".
  4. If there is none, 403. Otherwise return the team.
Used by85 endpoint parameters, e.g. dataset upload and listing, asking a question, dashboards, audit trail.
WhyThe client chooses the team id, so it cannot be trusted; this membership query is what stops a user from simply typing another team's id.

  4. 4
    get_current_team

  5. 5
    Endpoint runs

    Receives user and team already checked, and filters with Dataset.team_id == team.id.

    Any check fails

6. Known limitations

Passwords over 72 bytes

bcrypt 5.0 (the pinned version) raises ValueError for passwords longer than 72 bytes. I confirmed this for both hashpw and checkpw. Sign-up only checks the minimum length (8), and there is no global error handler, so such a password would cause an HTTP 500 instead of a clear 400 message. Fix: reject passwords over 72 bytes in signup().

No token revocation

Tokens cannot be cancelled before they expire (see the logout question).

datetime.utcnow()

Deprecated in Python 3.12 in favour of datetime.now(timezone.utc). It still works today.

7. Likely viva questions

Why bcrypt and not SHA-256 for passwords?

SHA-256 is designed to be fast, so an attacker can try billions of guesses a second. bcrypt is deliberately slow and adds a random salt to every hash, which makes guessing and pre-computed tables impractical.

What is inside our JWT, and is it encrypted?

sub (user id), email, iat and exp. It is signed, not encrypted: anyone can read the payload, but nobody can change it without the secret key. That is why no password or secret is put in it.

Why is sub stored as a string?

The JWT standard says sub is a string, and PyJWT validates that. The code converts it back with int(payload["sub"]).

What is Depends()?

FastAPI's dependency injection. An endpoint lists what it needs; FastAPI runs those functions first and passes in the results. If one raises an exception, the endpoint never runs. Because get_current_team depends on get_current_user, you cannot get a team without logging in first.

A user changes X-Team-Id to another team's id. What happens?

get_current_team finds no active membership row for that user and team and returns 403. On top of that, endpoints check that each row they load belongs to team.id and return 404 otherwise.

How does logout work if the server keeps no sessions?

The client deletes its token. The token itself stays valid until it expires (7 days). Revoking tokens early would need a deny-list, which this project does not have yet.

Why 401 vs 403?

401 means "we don't know who you are" (no or bad token). 403 means "we know who you are, but you are not allowed" (not a member of this team).
